Branch `step2b-root-cause` (from Step 2A commit `43c3a9e`). Analysis only: **no RTL, Python-model, weight, fault-database, detection-table, or baseline change was made** (checksum-verified, test B07). Eq.(2) weights unchanged; no new scheduling policy.
Reproduce: `python3 python/step2b_analysis.py` (writes `results_step2b/*.csv|json`, includes RTL cross-check of all 117 episodes), `python3 python/check_step2b.py`.
Methodology separation: the *first-detection campaign* (fault-free schedule replay, `fault_results.csv`) and the *closed-loop episodes* (one persistent fault per episode, `closed_loop_episodes.csv`) are never mixed. The 117 cases come only from the closed-loop evidence profile (`s2a_all3_evid`, 2,515 episodes, 2,451 flagged); the coverage-gap analysis uses only first-detection results (2,515 faults). Single mission trace, single injection seed 4242: **no multi-seed robustness is claimed.**

## 1. Root cause of the 117 flag-clearance episodes
All 117 were traced tick-by-tick (`flag_clearance_cases.csv`, per-tick events in `flag_clearance_traces.csv`). Single root cause, class `PARTIAL_SCAN_NON_OBSERVING`:
- In the implemented detection tables, `detect_partial=0` for all 117 faults (while `detect_full=1` for all; 56 regfile faults also `detect_mbist=1`).
- The DEGRADED scheduler only ever runs `PARTIAL_SCAN+DIAG` on a flagged block. The `DIAG` component has **no detection table** (it never detects any fault; `fault_campaign.detects()` returns 0, test B01), so the decision result equals the partial-scan result, which is PASS for these faults (117/117 diag decisions PASS).
- Lifecycle (e.g. F00009, safety SA0): injected tick 122; ONLINE test fails at tick 123 (`res_fail`); `dfault/unres/degmask` set at 124; DEGRADED at 125; PARTIAL+DIAG PASS at 125, 126, 127; `unres` cleared at 126 (first pass), `okc`=1,2; flag cleared at 128 (`okc` reached 3); the next ONLINE test fails again at 131 and the cycle repeats.
- Population evidence (test B02): over all 2,451 flagged episodes, clearance-while-fault-persists occurs **iff** `detect_partial=0` (117 of 117 vs 0 of 2,334).
- Counting check (B04): 119 faults are partial-blind but detectable elsewhere = 117 flagged-and-cleared + 2 injected too late to be detected.
Alternative causes examined and **excluded**: fault persistence (tables are static; all 117 re-fail later when a capable test runs, first re-failure median 4 ticks after clearance); episode bookkeeping (instrumented trace reproduces the Step-2A episode flag/clear ticks for all 117; closed-loop first detection equals replay, asserted in the Step-2A runner); flag/first-detection semantics mismatch (see below - this is part of the explanation, not a second bug); RTL/Python state-update or tick-ordering discrepancy (the exact `res_fail` stream of every episode replayed through the RTL: **117/117 RTL==Python, all 52 columns/tick**).
Consequences: `unres` clears after a single non-observing pass, so the unresolved-evidence guard on the fairness slot is released immediately; the flag then clears after `recov_n`=3 passes; the block flaps (flag cycles per case: min 2, median 18, max 76; 2,562 flag-set events in total).

## 2. Does partial-scan observability explain the anomaly?
Yes, **within the implemented behavioural model**: all 117 and no other flagged episode. It is demonstrated from the tables and logs, not assumed. Whether a physical partial scan would miss these faults is outside the model. Why Step 1 did not see it: Step 1's closed-loop helper (`run_closed_loop`) assumes a block-level fault fails every FULL/PARTIAL/DIAG component (full observability); the campaign detection model is fault-specific. The two diagnostic-evidence semantics differ, which is the "flag vs first-detection semantics" mismatch.
Classification as defect: the documented design (Step 1 report: recovery = `recov_n` consecutive passing DIAG decisions, "PARTIAL+DIAG in DEGRADED") explicitly allows a PARTIAL+DIAG pass to clear. So this is **a confirmed validity gap of the documented design, not a divergence from it, and not an RTL/Python defect**. I therefore implemented no fix (a fix changes diagnostic semantics and needs a policy decision, below) and added characterization tests only (B01-B04). If you want it treated as a defect, the minimal fix is described in section 7.

## 3. Diagnostic observability (`per_block_test_observability.csv`)
Under the implemented tables: FULL detects 2,513 of 2,515 faults (2 faults, F00532 and F00455, both motor SA1, are undetectable by every test); `detect_partial=1 => detect_full=1` holds for all faults (0 violations), so a full scan dominates a partial scan. Partial-scan detects 2,394; partial-blind but detectable elsewhere: safety 9, motor 28, encoder 14, comm 12, regfile 56 (119). Fraction for which a partial PASS is genuine absence evidence: safety 0.928, motor 0.948, encoder 0.945, comm 0.944, regfile 0.958. MBIST exists for regfile only (1,305 detectable); ONLINE detects 2,285 faults only in specific mask slots (4-slot rotation, so a passing ONLINE test says little). `DIAG` carries no observability at all. The manager receives only a per-block pass/fail bit: it cannot tell "fault absent" from "this test could not observe it", and it does not know which test class raised the failure. A DEGRADED-state PASS therefore counts as clearing evidence regardless of depth. Missing information for a correct rule: (a) failure-source test class on `res_fail`, (b) a depth ordering (FULL >= PARTIAL is verified from the tables; MBIST/ONLINE are not comparable with partial), (c) an escalation path so a flagged block can run a diagnostic deep enough to clear it. None is invented here.

## 4. Why adaptive misses faults that N=20 detects (`missed_faults.csv`)
64 faults are undetected by adaptive (Step 2A evidence profile): 2 undetectable by any test and **62 detected by N=20**. All 62: injected at tick 581-598 (1-18 ticks before mission end); **zero** capable tests executed on the block after injection; N=20 detects every one with its FULL scan at tick 599 (the last tick; test B06). Adaptive's last full scans of any block are ticks 577-581, with mean inter-scan gap 27-28 and max gap 86-90 ticks (regfile 55). Evidence-supported categories: 35 `NO_MISSION_IDLE_WINDOW_BEFORE_MISSION_END` (no mission-idle tick remained), 27 `IDLE_WINDOW_PRESENT_BUT_SWEEP_REARM_GAP_NOT_ELAPSED` (2-8 IDLE ticks existed but all had no decision: the idle sweep re-arms only after `sweep_gap`=10 ticks). No fault was withheld by an unresolved diagnostic (0 `fcause==4` ticks; the evidence profile never enters DEGRADED in the fault-free replay). 4 of the 62 had ONLINE tests run on their block, none in a capable slot (test ran but could not observe).
Coverage vs injection tick (detected/total, `root_cause_summary.json`): for every injection tick <= 580 all three of N=20, Step-1 and evidence profiles detect every detectable fault (2,436/2,438 over ticks 0-580; the 2 misses are the undetectable faults); for ticks 581-599: N=20 77/77, Step-1 and evidence 15/77. **The 0.9746 vs 0.9992 coverage gap is therefore a finite-horizon (mission-end) effect, not a steady-state coverage loss**, and N=20's 0.9992 depends partly on its periodic scan landing on the final tick. This does not mean adaptive is as good: its detection delay is larger (below), so the same effect would appear at any mission end, just with a longer window (~up to 55-90 ticks vs N=20's 20).

## 5. Latency on the 2,451 faults detected by both (`detection_latency_comparison.csv`)
Mean/median/p95 (cycles): N=20 207,033 / 207,965 / 382,898; Step-1 343,846 / 267,088 / 886,900; evidence 348,667 / 268,036 / 902,502; adaptive is slower on average (+141,634) but faster for 44% of faults. By block (mean, N=20 vs evidence): safety (tier 4) 187,253 vs 150,221 (adaptive faster); motor 197,817 vs 235,276; encoder 195,660 vs 192,556; comm (tier 2) 199,364 vs 391,555; regfile (tier 1) 216,404 vs 440,800. The cost is concentrated in low-priority blocks, which in the ACTIVE state receive ONLINE tests rarely and otherwise wait for idle full scans. (Detections by adaptive: 1,771 FULL_SCAN, 680 ONLINE.) This latency, not coverage, is the substantive weakness. Detected-only latency excludes the 62 N20-only faults; the censored means are in the CSV.

## 6. Starvation and test-selection semantics (what the implementation can distinguish)
Distinguishable and recorded: full-scan completion (`lastfull`/sweep bit set at the FULL decision tick, regardless of pass/fail; assumes completion within the tick); partial-scan completion (counted, never updates `lastfull`; test E12); eligible-but-not-selected, state-prohibited, gap-blocked and diagnostic-withheld fairness slots (`fcause` 5, 1, 3, 4). **Not distinguishable by the manager:** "test ran but cannot observe the fault" vs "fault absent" (no observability notion; only the campaign tables know), and "capable but failed to detect" (impossible by construction: a capable test always detects; ONLINE capability depends on a slot mask the manager does not see). Those cases are separable only offline from the fault tables (as done here). The 16-bit `lastfull` modular age and its >65,535-tick aliasing horizon are unchanged from Step 2A (the Step-2A rollover tests were re-run, see section 8).

## 10. Recommendations for the priority-policy redesign (evidence-based, not applied)
1. Evaluate coverage with a horizon-robust metric (detection-latency CDF / coverage for injections at least H ticks before end, plus censored latency); do not rank policies on end-of-mission coverage.
2. Target latency for low-tier blocks (comm, regfile): their mean latency is ~2x N=20 while safety is faster; a bounded idle-scan period per block would address the 27-tick mean / 55-90-tick max inter-scan gaps. The `sweep_gap`=10 re-arm rule explains the 27 idle-window misses.
3. Make diagnostic evidence observability-aware and add an escalation path (section 7) before any further DEGRADED-policy work; otherwise flap cycles (median 18 per affected episode) waste DEGRADED partial scans.
4. Repeat on multiple mission/injection seeds before any claim.
